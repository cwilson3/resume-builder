1. What is being compared

Resume Builder has two front ends, or shells, over one set of pure TypeScript modules. Parsing, the document model, serializing, the HTML preview, and the PDF writer are shared, so the only thing that differs is how each shell turns a change into updated DOM. The assessment measures that shell cost, three ways:

RowWhat it isBuilt from
vanillaThe hand-wired DOM shell (src/main.ts). Rebuilds the whole editor on every structural edit.npm run build in the repository root → dist/index.html
React, initial portThe React shell as first ported, before any optimization.Commit 080c53c, rebuilt by npm run perf:build-initial → resume-builder-playwright/perf/builds/react-initial.html
React, optimizedThe current React shell, with memo on the editor cards and the preview pane.npm run build in resume-builder-react/ → resume-builder-react/dist/index.html

Keeping the initial port as its own row is what makes the comparison useful: it separates what moving to React costs by itself from what one optimization won back. The shared modules are measured once on their own (npm run bench in the root), so the browser numbers can be read as shell cost on top of a common baseline.

2. What is measured

Each build loads the same generated resume and runs the same scenarios. There are two resumes: stress-50x10.md (50 entries, 500 bullets) and stress-200x10.md (200 entries, 2,000 bullets). The sample resume is far too small to show any difference.

ScenarioReported asWhy it matters
Single keystroke in a bulletTime to the editor's next paint, and to the preview's next paint, with the 120 ms refresh delay and with it off (?debounce=0)What a person feels while typing, and what each shell costs per keystroke
Sustained typing: 200 characters at one every 100 msScript and layout time, long tasks, with and without the delayThe cost of a realistic burst, which single keystrokes cannot show
Structural edits: + Entry, Delete entry, move a block, move a section, UndoClick to the next paint, with the delay offWhere React's keyed updates should beat vanilla's full editor rebuild
Cold open of the built page, with the resume already storedTime until the editor is rendered, first contentful paint, start-up script time, heap, page sizeStart-up cost and page weight, which React adds to

Every measurement runs on a production build opened from disk, in headless Chromium with the CPU slowed 4×. Latency runs from the input event to the next frame after the change, which approximates the next paint. All of it is measured from outside the page, so no shell carries instrumentation of its own. resume-builder-playwright/perf/README.md explains each of these choices and what it costs in run time.

3. How to read the results

  • The debounced numbers are the headline; the ?debounce=0 numbers are the diagnosis. With the 120 ms delay, the preview waits until typing pauses, which is what a person sees. With it off, both shells refresh in the same task as the keystroke, exposing each one's full cost. The two are never added or averaged together.
  • Latencies are "median / worst p95". The median of the three runs' medians, then the worst of the three runs' 95th percentiles. Medians keep one stall from moving the headline; the worst p95 shows whether stalls happen at all. Means are never used.
  • Per-run totals are "median run (range)". For example, script time over the 200-character burst: the median of three runs, with the lowest and highest in brackets.
  • Structural edits are timed only with the delay off. With it on, vanilla refreshes the preview 120 ms after a structural edit while React does it at once, so the two would be doing different work.
  • Ratios are the result, not absolute times. The numbers depend on the machine and the throttle. Compare rows within one run, and compare runs by their ratios.
  • These are lab samples, not INP. The frame after a change approximates the paint; it is not a presentation timestamp, and the lab figures are not the field metric Interaction to Next Paint.
  • Heap is one reading after load, including garbage not yet collected. Differences of a couple of MB are noise.

4. The reference numbers

These were measured on the prototype this repository was cleaned up from, on Oct 25–26, 2026: an Apple M2 Pro, 16 GB, Chromium 148 from Playwright 1.60.0, CPU throttled 4×, 3 runs × 50 iterations. The prototype built the master resume into the page and had an older toolbar, so its absolute numbers are not this repository's. They are kept unchanged as a point of reference in resume-builder-playwright/perf/prototype-reference/.

What it says

  • Where React helps: every structural edit. Keyed reconciliation updates only the cards that changed, while vanilla rebuilds the whole editor.
  • Where React costs: script time per keystroke, editor start-up, and page weight.
  • What closed the typing gap: memo on the editor cards and the preview pane, with stable callbacks, so a keystroke re-renders only the card being typed in. It cut React's debounced typing script by 82% at 200 entries and 71% at 50.
  • What it does not change: what a person feels while typing is the same in all three. The shared modules cost about 1.6 ms a keystroke unthrottled, so nearly all the measured cost is the shell and the browser's layout.

The full tables for both resumes, the shared-module benchmark, and the limits are in resume-builder-playwright/perf/prototype-reference/RESULTS.md.

5. Getting fresh numbers

Before you start

  • Node 24 (the version in the root package.json engines).
  • A clone of the repository with git access to GitHub: building the initial port may fetch refs/pull/6/head from origin.
  • About 4.5 hours of machine time for a full run, with the machine on mains power and kept awake.
  • Nothing else heavy running. Every other process competes for the CPU and shows up in the numbers.
  1. Install all three packages, root first, because the shared modules resolve their own dependencies from it: 
    npm ci
(cd resume-builder-react && npm ci)
cd resume-builder-playwright
npm ci
npx playwright install chromium
  2. Check the harness with a smoke run of about 3 minutes. It builds nothing, so build the three pages first, and it writes outside the repository so it cannot overwrite results: 
    npm --prefix .. run build
npm --prefix ../resume-builder-react run build
npm run perf:build-initial
PERF_RUNS=1 PERF_N=4 PERF_COLD=2 PERF_FIXTURES=stress-50x10 PERF_OUT=/tmp/perf-smoke \
  npx playwright test -c playwright.perf.config.ts
    Three tests should pass, one per build. If one fails, fix that before spending hours on a full run.
  3. Start the full run where it can keep going unattended. On macOS, caffeinate -i stops the machine sleeping while it runs; nohup keeps it going if the terminal closes: 
    nohup caffeinate -i npm run perf > perf-run.log 2>&1 &
    npm run perf builds all three pages, rebuilds the initial port, runs every scenario on both resumes, and renders the tables. On Linux or Windows, drop caffeinate -i and keep the machine awake another way.
  4. Follow progress in the log. A line appears as each build finishes on each resume (six in all), and its JSON is written to perf/results/raw/ as soon as its typing and editing phases are done: 
    tail -f perf-run.log
ls -l perf/results/raw/
  5. Read the tables in perf/results/tables.md, generated when the run ends. To regenerate them from the JSON (after changing the report, say), build the three pages first, because the page-size column is measured from the builds on disk: 
    npm run perf:report
  6. Add the shared-module baseline, from the repository root: 
    npm run bench
  7. Keep the results. Commit perf/results/raw/*.json and perf/results/tables.md together, and say in the commit which settings you used if they were not the defaults. Never write over perf/prototype-reference/.

Settings

VariableDefaultEffect
PERF_FIXTURESbothstress-50x10, stress-200x10, or both, comma-separated
PERF_SHELLSall threeany of vanilla, react-initial, react-optimized
PERF_RUNS3runs per build and resume
PERF_N50iterations of each scenario per run; keep it even, because moves are done in pairs
PERF_COLD10cold opens per run
PERF_OUTperf/results/rawwhere the JSON is written; use it for smoke runs

The settings are passed to npx playwright test -c playwright.perf.config.ts, or put in front of npm run perf. Each JSON file records the settings, the machine, and the Chromium version it was measured with, and the tables print them above each resume's results.

6. How long it takes, and shorter runs

RunAbout
Smoke run (above)3 minutes
50-entry resume, one build5–6 minutes
50-entry resume, all three builds15–20 minutes
200-entry resume, one build45 minutes to 2 hours
Everything: both resumes, all three builds4.5 hours

Nearly all the time is the 200-entry resume. Each run there repeats about 450 measured actions, two 20-second typing bursts, and the cold opens, on a 2,000-bullet page with the CPU slowed 4×, one at a time. The setup is chosen for accuracy, and the long run is a side effect; resume-builder-playwright/perf/README.md lists each choice and what it costs.

Shorter runs trade accuracy for time. Say which one you used whenever you quote the numbers:

  • Only the 50-entry resume (PERF_FIXTURES=stress-50x10), about 20 minutes. You lose the large-page results, where the structural-edit difference is largest.
  • Fewer runs or iterations (PERF_RUNS, PERF_N). Time falls about in proportion, but the 95th percentiles get unreliable below about 50 iterations, and one run cannot show a stall that hits a whole run.
  • Two builds instead of three (PERF_SHELLS=vanilla,react-optimized), a third less time. Without the initial-port row, the table can no longer say what the optimization won.

7. Comparing a new run with the reference

  • Compare ratios, not milliseconds. A different machine, Chromium version, or page will move every absolute number. The questions are whether React still wins structural edits by about 2×, how much script time per keystroke it still adds, and whether the initial-port gap is still about what the reference shows.
  • Expect start-up and page size to differ most. This repository's page fetches the master instead of carrying it, and has a Download dialog and a welcome panel the prototype did not. The editing scenarios load a stress resume first, so they move less.
  • Check the run's header line in tables.md (Chromium, machine, throttle, runs × iterations) before comparing anything.
  • Look at the "Stuck loads replaced" column. Anything above zero means a cold open hung and was replaced (see below); the row is still valid, but worth a note.

8. Troubleshooting

SymptomCause and fix
Executable doesn't exist when the browser launchesThe Chromium build for the pinned Playwright is not installed. Run npx playwright install chromium in resume-builder-playwright.
perf:build-initial says the commit is not reachableIt fetches refs/pull/6/head from origin; check that origin points at the GitHub repository and that you can fetch from it.
The React build fails to resolve jspdfThe root package is not installed. Run npm ci in the repository root first.
A test fails with "No block starting …"The stress resume on disk is not the generated one. Run npm run perf:fixtures; it rewrites both files exactly.
Page size shows ?A build was missing when the report ran. Build all three, then npm run perf:report.
A cold open hangs, then the run carries onKnown and unexplained: after the long typing phases, a load occasionally never finishes. The harness gives each one 30 seconds, records it, and replaces it; more than three fail the test. The typing data is saved before the cold opens begin, so nothing earlier is lost.
Numbers far noisier than the referenceSomething else was using the CPU, or the machine throttled or slept. Close other apps, stay on mains power, use caffeinate, and run again.
